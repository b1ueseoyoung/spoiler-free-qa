# 소설 도우미 확장 계획 (2026-10-14, 1차 완료)

## 목표와 완료 기준

- **목표:** 「탁류」 전용 도우미를, 저작권이 끝난 한국 장편 여러 편 가운데 하나를 골라 지금과 같은 방식으로 묻는 "소설 도우미"로 바꾼다.
- **완료 기준:**
  - 첫 화면에서 작품을 고르면, 그 작품의 장 목록과 대화 화면이 나온다.
  - 작품마다 "N장까지" 검색, 인용 검증, 거절 문구가 그 작품의 장 수에 맞게 동작한다.
  - 「탁류」의 기존 평가 결과와 카세트가 그대로 재현된다(`uv run pytest` 전체 통과, 녹화 재생 포함).
  - 로컬(LM Studio)과 공개 데모(Lambda) 모두에서 동작한다.
- **하지 않는 것:** 새 작품의 정답지와 평가 실험(사용자 결정). 새 작품은 "평가하지 않음"으로 표시한다.

## 작품 후보 (조사·검증 결과)

모두 위키문헌에 있고, 작가가 1962년 이전에 사망해 한국에서 저작권이 끝났다. 원문은 끝까지 있다.

| 작품 | 작가(사망) | 장 | 분량 | 정제 난이도 | 판단 |
| --- | --- | --- | --- | --- | --- |
| 「태평천하」 | 채만식(1950) | 15 | 16.6만 자 | 쉬움(지금 정제기로 오류 0) | 넣기. 마지막 장 반전이 있어 기능을 보여 주기 좋다 |
| 「상록수」 | 심훈(1936) | 17 | 25만 자 | 쉬움(제12장 깨진 태그 1곳) | 넣기. 교과서 수록작 |
| 「운현궁의 봄」 | 김동인(1951) | 25 | 20만 자 | 쉬움(장 제목 없이 한자 숫자 소제목) | 넣기 |
| 「무정」 | 이광수(1950) | 126 | 32만 자 | 보통(7묶음을 장으로 나누기, 머리말의 줄거리 요약 제거) | 넣기. 인지도 최상. 장 선택 UI 필요 |
| 「적도」 | 현진건(1943) | 22 | 22만 자 | 보통(한 페이지를 장으로 나누기, 줄바꿈 이어 붙이기) | 2차 |
| 「벽공무한」 | 이효석(1942) | 16 | 26만 자 | 보통(하드 줄바꿈 약 4,300곳 이어 붙이기) | 2차 |
| 「무영탑」 | 현진건(1943) | 164 | 33만 자 | 보통(9묶음, 장이 매우 많음) | 2차, 조건부 |

- **1차 제안:** 「탁류」 + 「태평천하」, 「상록수」, 「운현궁의 봄」, 「무정」(모두 5편)
- **주의:** 「무정」의 위키문헌 머리말에는 20장 분량의 줄거리 요약이 들어 있다. 이것을 본문에 섞으면 그대로 스포일러가 되므로 정제에서 반드시 버리고, 테스트로 막는다.

## 화면과 이름

- **이름(정할 것):** 예: **책갈피**(읽은 데까지만 답한다는 뜻). 「탁류」 고유 문구(제목, 워드마크, 예시 질문, 출전)는 작품 정보에서 채운다.
- **첫 화면:** 작품 카드 목록(제목, 작가, 연재 연도, 장 수, 스포일러 없는 한 줄 소개). 소개는 첫 장 내용 범위로만 쓴다.
- **작품 화면:** 지금 대화 화면과 같다. 상단에 "다른 소설 고르기"를 둔다. 주소에 작품을 넣어(`#/taepyeong`) 링크로 공유할 수 있게 한다.
- **장 선택:** 30장 이하는 지금처럼 번호 칸, 「무정」처럼 많으면 숫자 입력이나 묶음(1~20장 …) 선택으로 바꾼다.

## 데이터와 코드 구조

- **작품별 폴더:** `data/works/<id>/`
  - `work.json`: id, 제목, 작가, 사망 연도, 출처, 라이선스, 장 수, 프롬프트용 이름, 수집·정제 방식
  - `raw/`, `clean/`, `sources.json`(판 고정), `clean-report.json`, `entities.json`, `index/<모델>/`
- **「탁류」 옮기기:**
  - 폴더만 `data/works/takryu/`로 옮긴다. 임베딩은 다시 계산하지 않는다.
  - 프롬프트용 이름은 지금 문자열과 한 글자도 다르지 않게 둔다. 카세트 키가 프롬프트 전문으로 만들어지기 때문이다.
- **코드:** 「탁류」에 고정된 곳 57곳(코드 정찰 결과)을 `Work` 하나로 모은다.
  - 장 수(19)와 마지막 장, 경로, 프롬프트의 작품명, 거절 문구의 마지막 장
  - 웹 API: `/api/works`, `/api/chapters?work=`, `/api/ask`에 `work` 필드
  - 화면, CLI의 `--work`
  - 정답지·평가 명령은 「탁류」로 고정한다.
- **수집기 일반화:** 작품마다 수집 방식을 고른다.
  - 장별 하위 페이지: 탁류, 태평천하, 상록수, 운현궁의 봄
  - 묶음 페이지를 소제목으로 나누기: 무정
  - 한 페이지를 제목으로 나누기: 적도
- **정제기 보강:**
  - 지울 틀을 허용 목록으로 둔다. 모르는 틀은 실패시킨다. 지금은 모든 틀을 조용히 지워서 본문이 사라져도 모른다.
  - 하드 줄바꿈 이어 붙이기, 줄거리 요약 제거
- **실행:** 작품마다 색인과 Verifier를 처음 쓸 때 올린다. 임베딩 모델은 하나를 같이 쓴다.

## 스포일러 방어 (새 작품에 그대로 적용되는지)

- **인물 첫 등장표가 필요하다.** C4는 답 본문에 N장 뒤에 처음 나오는 인물이 있으면 막는데, 이 표가 그 판단에 쓰인다.
  - 제안: kiwipiepy(이미 쓰는 형태소 분석기)로 고유명사 후보를 뽑는다. 3회 이상 나온 것만 남기고, 첫 등장 장은 코드로 계산한다.
  - 결과는 "사람 검토 전"으로 표시한다. 비용은 들지 않는다.
- **알려진 약점(정찰에서 찾음):** 확인된 인용이 하나라도 있으면, 다른 인용이 N장 뒤에만 있어도(L1) 답을 보여 준다.
  - 유명한 작품(무정, 상록수)은 모델이 결말을 알 가능성이 「탁류」보다 높다.
  - 제안: C4에서 N장 뒤 인용이 하나라도 있으면 거절하도록 강화한다.
  - 「탁류」 test는 C3 응답을 다시 써서(카세트) 무료로 재채점한 뒤, 결과를 비교해 기록한다.

## 단계

1. 지금 브랜치(`omo/claude-deploy`) 커밋 → `omo/novel-expansion`
2. `Work` 도입과 「탁류」 옮기기 → 확인: `uv run pytest` 전체, 녹화 재생 테스트, `gold-check`가 그대로 통과
3. 수집·정제 일반화, 1차 4편 받기 → 확인: 작품마다 장 수, 남은 마크업 0, 줄거리 요약 0(테스트)
4. 인물표 자동 생성, 작품별 색인(LM Studio와 서버용 GGUF 두 가지)
5. 웹 API와 첫 화면, 작품 화면, 이름 → 확인: 로컬 브라우저에서 작품마다 질문 1개씩(로컬 모델)
6. (선택) C4 강화와 「탁류」 재채점
7. 배포 → 확인: 공개 주소에서 작품마다 질문 1개(약 15센트), 준비 요청 시간 측정
8. README, decisions.md, 한계 문서(새 작품은 평가하지 않음)

## 진행 (2026-10-14)

- 1~5단계와 7단계를 마쳤다. 6단계(C4 강화)도 했다. 이름은 책갈피다.
- 결정과 확인 결과는 `docs/decisions.md`의 "책갈피: 여러 작품으로 넓히기"와 "코드 리뷰 반영"에 있다.
- 공개 데모에 5편을 배포했다. 작품마다 예시 질문 하나씩 답과 인용(N장 이하)을 확인했다.
- 남은 일(사용자 확인 필요): 커밋과 push, 지난 커밋 작성자 이메일 바꾸기(강제 push), 저장소 공개와 PR, 권한 경계 적용(`docs/deploy-plan.md`).

## 위험

| 위험 | 대응 |
| --- | --- |
| 「탁류」 카세트가 깨진다 | 프롬프트 문자열을 그대로 두고, 녹화 재생 테스트로 매 단계 확인한다 |
| 정제 중 본문이 조용히 사라진다 | 틀 허용 목록, 장마다 글자 수 보고서 |
| 머리말 줄거리 요약이 섞인다 | 정제에서 제거하고, 테스트로 "장 본문에 요약 문장 없음"을 확인한다 |
| 유명 작품에서 기억 누출 | C4 강화(선택), 한계 문서에 "새 작품은 평가하지 않음"을 적는다 |
| 이미지·메모리 증가 | 작품당 색인 약 3MB라 영향이 작다. 배포 뒤 준비 시간을 다시 잰다 |

## 일정

- 1차 4편 기준 하루 반에서 이틀. 2차(적도, 벽공무한, 무영탑)는 수집 방식만 더하면 반나절이다.
- 커밋과 push는 요청할 때만 한다.
